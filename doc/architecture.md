# 架构

## 分层

- BFF/API 层负责端侧体验，不做分布式事务协调器。
- BFF 可做 DTO 适配、认证上下文、粗粒度权限、版本兼容、缓存、限流、降级。
- BFF 不直接连接业务库，不拥有领域数据。
- 内部服务拥有自己的领域数据和业务规则。
- 服务之间通过 RPC 或事件协作，不 import 其他服务的 `internal`。
- `common` 只放公共 proto、客户端、基础工具和跨服务约定，不承载具体业务流程。

## 读写边界

- BFF 写接口通常只调用一个内部归属服务的命令接口。
- BFF 不聚合同步跨服务写；确需多服务写时，必须先设计 Saga/TCC/补偿。
- BFF 读接口可以聚合多个内部服务，允许短暂最终一致。

- 主业务写入放在归属服务内完成本地事务。
- 跨服务副作用通过 outbox + MQ 异步触发。
- 消费侧需要幂等、重试、补偿时使用 inbox。
- BFF 不直接发布领域 MQ 事件，优先由归属服务写 outbox。

## 文件边界

- 一个 proto 文件最多定义一个 `service`。
- 每个 proto service 对应一个 Go service 文件。
- 常规表业务尽量保持 proto、service、biz、data、schema 一一对应。
- 复杂业务应新增明确业务 usecase，不使用泛化 helper 承载流程。
