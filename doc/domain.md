# 领域建模

## 数据模型

- 模块内部实体使用业务概念本身，不重复模块名。
- 数据库表名保留服务或模块前缀，便于共库排查和运维识别。
- 常规业务表使用统一审计字段，如 `created_at`、`updated_at`。
- 可缺省扩展表允许不存在记录，通过 upsert 按归属键更新。
- 登录、审计、行为流水等历史事实优先建日志表，不塞进主实体。
- JSON 字段只用于结构可变、查询要求不强的内容。

## 约束与索引

- 唯一约束必须对应真实业务幂等或业务唯一性。
- 索引根据查询接口和补偿扫描设计，不提前为未知查询堆索引。
- 复合索引顺序按过滤、排序、扫描方式设计。
- Ent schema 中表、字段、关键索引应保留中文注释。

## Usecase 与 Repo

- service 层负责协议适配；usecase 层承载业务规则、事务编排、事件写入。
- repo 层只负责数据访问，不承载跨业务流程。
- usecase 可以按业务层级调用其他 usecase，但必须明确上下游，禁止循环调用。
- 一个写流程只能有一个清晰事务入口。
- repo 方法不要为复合条件拼接超长 `ByXxxAndYyy`；复杂条件使用 `Query`、`Filter`、`Spec` 参数对象。

## 枚举

- 跨服务、跨层或落库约束枚举必须定义 proto enum。
- 服务内部使用 string enum 表达领域语义和数据库值。
- 内部枚举通过 `common/pkg/enum.Mapping` 绑定 proto enum。
- Ent enum values 使用 `XxxMap.EnumValues()`。
- 落库枚举使用内部 string enum，不直接持久化 proto 数值。
